1What this scaffold gives you

You write plain text. The build turns it into a funder-compliant PDF and a matching Word file — and then measures them, refusing to hand you output that breaks a rule. Fonts, margins, footers and citation numbering are not your problem.

You getHow
A4, 16 mm margins, Times at 11 pt, single spacing, page footerEncoded once in _quarto.yml + tex/msca-header.tex
A gate that measures the finished PDFscripts/check_msca_compliance.py — seven hard checks; the build fails on any of them
Word output styled to matchtex/msca-reference.docx, checked by the same gate
Compact numbered citationsreferences.bib + nature.csl
Live preview while writingscripts/preview.sh — hot-reloading HTML
A reproducible toolchainpixi.toml + pixi.lock, or the Docker image

Where the rules come from: the official MSCA application form, "Instructions for Drafting Part B". It is reissued each call — re-check it before reusing this scaffold for a new year. Two details worth knowing: the body font is TeX Gyre Termes, metric-compatible with Times New Roman and accepted under its other name Nimbus Roman No. 9 L (that is the answer if anyone asks why the form says "Times New Roman" and pdffonts says TeXGyreTermes); and captions, footers and figure labels may be smaller than the body but never below 8 pt.

Why the gate exists
A render once came out US Letter, in Latin Modern, with no page footer, because one file was missing from project.render and so never saw the tuned template. Nothing about that PDF looked wrong at a glance, and a page-count-only check passed it. Formatting is now measured, not eyeballed.

Two ways to get the toolchain. Pick one:

Route A — Pixi recommended for writing
Native install, fast renders, live preview, VS Code integration. This is what you want day to day. Go to §2.
Route B — Docker for frozen, offline, or rescue builds
A ~3.5 GB image with the whole LaTeX distribution baked in. Renders identically on any machine, in any year, with no network. Slower, and less pleasant to write in. Go to §3.

2Set up a clean laptop (Route A)

Roughly 20 minutes, most of it waiting on downloads. macOS shown; Linux is identical, Windows works the same via PowerShell.

1
Install VS Code — code.visualstudio.com. Then the two extensions this scaffold expects; VS Code offers them automatically, because they are listed in .vscode/extensions.json. 
code --install-extension quarto.quarto
code --install-extension ltex-plus.vscode-ltex-plus
2
Install Pixi, which manages every other tool. 
curl -fsSL https://pixi.sh/install.sh | bash
Open a new Terminal so the PATH change takes effect. Check with pixi --version.
3
Get your own copy. Clone it, then cut it loose from this repository's history so your proposal starts with a clean one. 
git clone <repo-url> my-proposal
cd my-proposal
rm -rf .git && git init && git add -A && git commit -m "start from the MSCA-PF scaffold"
4
Build the environment and the LaTeX engine. Both, in this order, from the folder containing pixi.toml. 
pixi install       # Quarto, Python, PyMuPDF, poppler — exact versions from pixi.lock
pixi run setup     # TinyTeX, a self-contained LaTeX distribution
The first render pulls any missing LaTeX packages from CTAN, so it needs a network connection once.
5
Prove it works. 
pixi run build
On an untouched scaffold the formatting passes and the placeholder check fails — which is correct, because you have not written anything yet: 
  [PASS] A4 page size                 (hard)
         all 3 pages 595x842pt
  [PASS] Times fonts, embedded        (hard)
         3 font(s), all embedded: TeXGyreTermes-Bold, ...
  [PASS] Font size >= 11 pt           (hard)
         histogram: 9.0pt:60ch, 11.0pt:2838ch, 12.0pt:76ch
  [PASS] Margins >= 15 mm             (hard)
         measured minima: top 16.8mm (p2), right 16.0mm (p1), bottom 20.7mm (p2), left 16.0mm (p3)
  [PASS] Footer 'Part B - Page X of Y' (hard)
         correct on all 3 pages, total resolves to 3
  [PASS] Page limit                   (hard)
         3/10 pages, 7 page(s) to spare
  [FAIL] No unresolved placeholders   (hard)
         10 found -- p1: '[acronym] 1. Excellence ...'
Replace the placeholders and that last line goes green too.
Open the folder that holds pixi.toml
That is the repository root. Open a parent folder instead and every pixi run fails with could not find pixi.toml, and the Quarto extension will not recognise the project.

3The Docker route

Route A depends on TinyTeX fetching LaTeX packages from the internet on first use. That step is networked and mutable, so it is the one part that can drift between machines or fail years later. The Docker image freezes it.

Use Docker when: you need a build guaranteed reproducible for archival or resubmission; you have no network; your local TeX install has broken; or you are building in CI.

amd64 only — not a preference
conda-forge publishes no quarto build for ARM Linux, so the environment cannot be solved on linux-aarch64. The image is therefore amd64, and on an Apple Silicon Mac it runs under emulation — slower, but identical for everyone. --platform linux/amd64 is required in every command.
# build once, from the folder holding pixi.toml (~10 min)
docker build --platform linux/amd64 -t msca:latest .

# render and validate everything — outputs land in _build/ on your real disk
docker run --rm --platform linux/amd64 -v "$PWD:/work" msca:latest

# prove it needs no network at all
docker run --rm --platform linux/amd64 --network none -v "$PWD:/work" msca:latest

# poke around inside
docker run --rm -it --platform linux/amd64 -v "$PWD:/work" --entrypoint bash msca:latest

The image deliberately does not run pixi at render time. The folder you mount carries its own .pixi/ built for your host OS, and using it inside a Linux container fails on platform mismatch. The image puts its own solved environment on PATH instead.

4The daily writing loop

1
Open the project. code my-proposal — the folder with pixi.toml in it.
2
Start the live preview once, in the VS Code terminal (Ctrl+`), and leave it running: 
pixi run preview
It serves http://localhost:4200/partB1.html. The port is fixed, so the URL never changes.
3
Put the preview beside your text. Either open that URL in a browser on a second monitor, or keep it inside VS Code: Cmd+Shift+P → Simple Browser: Show → paste the URL, then drag the tab to the right half.
4
Edit a file in sections/ and hit Cmd+S. The preview rebuilds in a few seconds and refreshes itself.
5
Run the real build every few paragraphs: 
pixi run build
This is the command that governs the document. Keep _build/partB1.pdf open in a viewer and it refreshes each time.
The preview shows prose, not pages
The live preview is HTML. It shows wording, structure and flow — it cannot show pagination, because HTML has no pages. Only pixi run build tells you whether you are over the limit. Never judge "did that edit fit?" from the preview.
Why a script instead of plain quarto preview
Two Quarto behaviours:
  1. quarto preview watches only the file you name. Files pulled in with {{< include >}} are not watched — so editing a section would leave the preview silently stale, showing old text with no error. scripts/preview.sh nudges the master file when a section changes.
  2. quarto preview pointed at PDF renders once and then fails on every subsequent rebuild. The live loop therefore runs on HTML, which reloads cleanly.

5Which file holds what

sections/ holds one file per scored sub-section. That is the only directory you normally open.

FileCriterion / weight
_1.1_objectives.qmd _1.2_methodology.qmd
_1.3_supervision.qmd _1.4_researcher.qmd		Excellence — 50%
_2.1_career.qmd _2.2_dissemination.qmd _2.3_magnitude.qmdImpact — 30%
_3.1_workplan.qmd _3.2_host.qmdImplementation — 20%
partB2.qmdCV, host capacity, ethics, security screening, Green Charter, AI declaration. No page limit.
references.bibBibliography — cite with [@key]
partB1.qmdStitches the nine sections in order. Build configuration, not content.
gantt.yaml, figures/Optional Gantt chart — see §10
_build/All rendered output. Generated — never edit, never store anything here.
One file, one evaluator question
The split is not cosmetic. Each file answers a question that is separately scored, so the thing you edit is the thing that gets marked. The build refuses to render if any of the nine is missing or emptied — that is how §1.4 gets lost, and it costs two scored questions when it happens.
Never keep anything in _build/
pixi run clean is rm -rf _build .quarto. A supervisor's commented Word file left there is one command away from gone.

6Formatting cheat-sheet

You writeYou get
**bold text**bold text — for the lines a busy reviewer skims
*italic text*italic text — species names, emphasis
## HeadingA sub-section heading (## = level 2, ### = level 3)
- itemA bullet point (dash, then a space)
[@smith2024]A citation — renders as a superscript number and joins the reference list
[@a2020; @b2021]Two citations at once
<!-- a note -->A hidden comment. Does not appear in the PDF.
| A | B |A table row. Keep the |---|---| divider under the header.
Blank lines matter
Leave one empty line between paragraphs. A heading, a bullet list or a table each need a blank line before and after, or they will not render as you expect.
Never use backticks in the proposal text
A markdown code span renders in Latin Modern Mono, which is not a Times family — the font check rejects it outright, because Latin Modern is the signature of a bypassed template. There is no Times monospace. Write the term in italics instead.
Unbalanced ** is the silent one
An opening ** without its closing pair prints literal asterisks into the finished PDF. The gate catches it, but you can find it faster: 
grep -n '\*\*' sections/*.qmd partB2.qmd | awk -F: '{n=gsub(/\*\*/,"",$0); if (n%2) print}'

7Adding a reference

1
Paste a BibTeX entry at the end of references.bib: 
@article{smith2024,
  author  = {Smith, Jane and Doe, John},
  title   = {An example paper title},
  journal = {Nature},
  year    = {2024},
  volume  = {600},
  pages   = {123--130},
  doi     = {10.1038/s41586-024-00000-0}
}
The word right after { — here smith2024 — is the key.
2
Cite it: …as recently shown [@smith2024]. Save, rebuild, and it appears with the right number.
Rule
Only cite keys that exist in references.bib. A missing key renders as a broken ?. Never invent a DOI — omit the field if you do not have one.

Prefer make? make build, make pdf, make b2, make preview, make check and make clean all exist. They do not go through Pixi — the Makefile calls quarto and python straight off your PATH, so that route needs Quarto, a TeX engine, poppler and PyMuPDF already installed.

What the gate measures

Seven hard checks, on every rendered PDF and every Word file. Any failure exits non-zero.

CheckRule
Output is currentthe file is newer than every source — a render that failed cannot be reported as one that worked
Page sizeA4, every page
FontsTimes family for body text, all embedded. Latin Modern rejected at any share; other faces warn when they cover a small part of the document (figure labels are allowed) and fail when they cover the body.
Font sizebody ≥ 11 pt; captions, footers and figure labels ≥ 8 pt
Margins≥ 15 mm all four sides, measured from the real content — images and vector ink included, so an oversized figure cannot slip past
FooterPart B - Page X of Y on every page, with a total that matches reality
Page limitPart B-1 ≤ 10 pages
Placeholdersno [...], TODO cite or stray ** surviving into the text

Plus three warnings that do not fail the build: cover page / table of contents, reference-list page span, and PDF version.

Why each document is rendered separately
scripts/render_all.sh renders one file at a time rather than using quarto render in project mode, which fails intermittently partway through with a rename … NotFound error — and leaves the previous PDF sitting in _build/, where it still measures as perfectly valid. That is why the freshness check exists as well.

9The page limit

Critical
Part B-1 must be 10 pages or fewer. The submission system makes everything past page 10 invisible to evaluators — an overflow does not error, it silently deletes your Implementation tables.
  • Page breaks jump in whole lines, because tables become longtables that cannot split gracefully. Judge a trim by the number the build prints, not by how much shorter the text looks.
  • The numeric citation style is already on (nature.csl) — that lever is spent. The remaining ones are structural: trim the reference list, convert a table to prose, or drop 1 mm of margin.

10Word output

pixi run build produces .docx alongside each PDF, styled to match: A4, 16 mm margins, Times New Roman 11 pt, the same footer. tex/msca-reference.docx supplies those defaults to pandoc; regenerate it with pixi run refdoc.

Word will not paginate like the PDF
Word and TeX break lines and justify differently, so the same text at the same size in the same column lands on different pages. The Word file matches on style, and its page count is indicative only. Submit the PDF, and treat it as the authority for the 10-page limit.

11A Gantt chart

The work plan ships as a markdown table, which is the cheapest thing that survives the page budget. If you want a drawn chart instead, edit gantt.yaml and run:

pixi run gantt

It writes figures/gantt.pdf and checks two things that would otherwise break the build:

CheckWhy
Width fits the 178 mm text columnQuarto scales an oversized figure down — and scaling a vector figure scales its text, so 8.7 pt labels arrive at 4.2 pt, under the floor and unreadable
Height fits the text blockA taller figure overflows the bottom margin, which the gate fails

Include it with ![Work plan.](figures/gantt.pdf). Budget roughly 0.85 of a page — a lot, when the cap is 10.

12Spelling & grammar

In the editor — LTeX

Grammarly's desktop app cannot attach to VS Code; do not spend time trying. The in-editor equivalent is LTeX+, which is offline and understands Markdown and LaTeX, so it will not flag [@smith2024] as a misspelling. It is configured in .vscode/settings.json; add your field's vocabulary there.

For a thorough pass — Grammarly via Word

1
pixi run proof — renders the Word file and opens it (macOS).
2
Review Grammarly's suggestions in Word, with the add-in.
3
Apply each fix you accept by hand, in the .qmd. Then rebuild and confirm the page count has not moved.
Never paste the Word text back over the .qmd
The round-trip has already turned [@key] into plain superscript numerals and flattened the tables. Pasting it back destroys every citation silently — they look fine until you rebuild and the reference list is empty.
Suggestions to refuse
Set Grammarly to Formal · Academic · Expert, and reject anything that removes a calibrated hedge — "to our knowledge", "may", "could", "candidate". Those words are load-bearing: deleting one upgrades a claim above the evidence behind it, which is the most damaging edit available in a proposal. Also refuse changes inside tables, and hyphens replacing en-dashes in ranges such as 2018–2023 or WP1–WP3.

13Version control

# before a risky edit
git add -A && git commit -m "before rewriting 1.2"

# see what changed
git diff

# throw away changes to one file
git checkout -- sections/_1.2_methodology.qmd

Do not hand-roll a backups/ folder — that ritual produces dozens of stray .bak files and git already does it properly.

pixi run hooks installs a pre-commit hook that blocks committing a PDF that fails the gate. It is belt-and-braces: _build/ is gitignored, so it only fires if a PDF is force-added.

14Never touch these

Leave alone
_quarto.yml, the tex/ folder, nature.csl, and scripts/. These enforce compliance — page size, margins, font, footer, citation numbering, and the gate itself. Editing them can break the rules in ways that are hard to see. In particular: do not add a cover page or a table of contents, and never shrink table text below the body size.

SymptomFix

Pre-submission checklist. pixi run build must exit 0 — that covers A4, fonts, sizes, margins, the footer, the page limit and leftover placeholders on every PDF and Word file · read the whole thing once, on paper · confirm the PDF is text-searchable, because evaluators keyword-search it · check the acronym in partB1.qmd matches Part A.
